# 유저스토리 작성 가이드

PRD 2번 섹션을 채울 때 따르는 형식과 정책입니다.
이 섹션이 PRD 안 모든 결정의 **근거**가 됩니다.

## 표준 형식

```
As a [역할], I want [기능], so that [목적].
```

- **역할**: 누가 이 컴포넌트를 사용/접하는가 (예: `사용자`, `관리자`, `폼 작성자`, `키보드 사용자`, `스크린리더 사용자`).
- **기능**: 컴포넌트가 제공하는 동작/속성.
- **목적**: 그 동작이 왜 필요한지 (사용자 가치).

번호: `US-1`, `US-2`, ... 순서. PRD Props 표의 "출처" 칼럼이 이 번호를 참조합니다.

## 좋은 유저스토리 예

```
US-1: As a 폼 작성자, I want 제출 버튼이 명확하게 강조되기를 원한다,
      so that 완료 액션을 즉시 인지할 수 있다.

US-2: As a 키보드 사용자, I want Tab 으로 버튼에 포커스하고 Enter 로 활성화하기를 원한다,
      so that 마우스 없이도 폼을 제출할 수 있다.

US-3: As a 사용자, I want 비동기 처리 중에 버튼이 비활성화되고 진행 표시를 원한다,
      so that 중복 제출을 막고 진행 상태를 알 수 있다.
```

## 나쁜 유저스토리 예 (피할 것)

- ❌ `버튼은 sm/md/lg 사이즈를 가진다` — 형식 미준수, 누가 왜 필요한지 없음.
- ❌ `As a 개발자, I want className 을 받기를 원한다` — 본 디자인 시스템에서는 모든 컴포넌트가 className 을 받는 것이 **공통 규칙** (`architecture/architecture03-naming.md`). 공통 규칙은 유저스토리로 쓰지 않습니다.
- ❌ `As a 사용자, I want 멋진 버튼을 원한다` — 측정 불가능하고 "왜"가 없음.

## 추적성 규칙 (★ 핵심)

PRD 의 모든 항목은 유저스토리에서 도출되어야 합니다.

- **Props**: `prd01-template.md` 의 Props 표 "출처" 칼럼에 US 번호 명시. 출처가 없으면 prop 을 빼거나, 유저스토리를 먼저 추가합니다.
- **Variants**: 각 variant 가 어떤 US 의 사용 케이스를 커버하는지 추적 가능해야 합니다.
- **States**: 각 state 가 왜 필요한지 US 에 근거가 있어야 합니다.
- **접근성**: PRD 7번 섹션 항목마다 출처 US 번호를 명시합니다.

## 공통 규칙 vs 컴포넌트별 규칙

다음은 공통 규칙이므로 유저스토리에 다시 쓰지 않습니다 — 자동 적용됩니다.

- `className?: string` 수용 (`architecture/architecture03-naming.md`)
- shadcn 시맨틱 토큰 사용 (`style/style01-tailwind-rules.md`)
- 키보드 접근 가능 + `focus-visible` ring (`style/style04-states.md`)

이외의 모든 결정은 유저스토리 근거가 필요합니다.
